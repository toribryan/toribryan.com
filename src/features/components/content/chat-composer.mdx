The box people write messages in, built from parts around one draft so each
chat surface uses only the parts it needs.

<Exhibit
  of="chat-composer.Default"
  title="Chat composer"
  description="Type and press Enter to send. Shift+Enter breaks the line, and files dropped on it attach."
>
<ExhibitCode label="Install">

```bash
npx shadcn@latest add https://fibo.toribryan.com/r/chat-composer.json
```

It installs fibo's Button, Progress and Tooltip with it, plus the
`--input-subtle` and `--ring-subtle` tokens.

</ExhibitCode>
<ExhibitCode label="Usage">

```tsx
import {
  ChatComposerCommonActions,
  ChatComposerFooter,
  ChatComposerFrame,
  ChatComposerInput,
  ChatComposerSubmit,
  LocalChatComposerProvider,
} from "@/components/ui/chat-composer"

export function ChannelComposer() {
  return (
    <LocalChatComposerProvider onSubmit={({ value }) => sendMessage(value)}>
      <ChatComposerFrame>
        <ChatComposerInput placeholder="Message #design" />
        <ChatComposerFooter>
          <ChatComposerCommonActions />
          <ChatComposerSubmit />
        </ChatComposerFooter>
      </ChatComposerFrame>
    </LocalChatComposerProvider>
  )
}
```

When a surface needs something the parts don't do, write it as JSX beside
them rather than adding a prop to a part.

</ExhibitCode>
<ExhibitCode label="Props">

`LocalChatComposerProvider` keeps the draft in component state:

| Prop                 | Type                                                      | Default | Description                                                                                               |
| -------------------- | --------------------------------------------------------- | ------- | --------------------------------------------------------------------------------------------------------- |
| `defaultValue`       | `string`                                                  | `""`    | The draft to start with.                                                                                  |
| `defaultAttachments` | `ChatComposerAttachment[]`                                | `[]`    | Attachments to start with.                                                                                |
| `onSubmit`           | `(message: ChatComposerMessage) => void \| Promise<void>` |         | Called with the draft on send. Return a promise to hold the draft until it settles; a rejection keeps it. |
| `disabled`           | `boolean`                                                 | `false` | Takes no input while true.                                                                                |
| `canSubmit`          | `(message: ChatComposerMessage) => boolean`               |         | Decides whether the draft may be sent. Defaults to having text or an attachment.                          |
| `inputRef`           | `RefObject<HTMLTextAreaElement \| null>`                  |         | A ref for the text box. One is made for you when omitted.                                                 |

`ChatComposerProvider` takes `state`, `actions` and `inputRef` instead, for a
draft that lives somewhere else. The parts take their element's props, plus:

| Part                        | Prop     | Description                                                                              |
| --------------------------- | -------- | ---------------------------------------------------------------------------------------- |
| `ChatComposerAction`        | `label`  | Names the icon for screen readers and the tooltip.                                       |
| `ChatComposerAttachButton`  | `accept` | File types the picker offers, as in a file input's `accept`.                             |
| `ChatComposerAttachButton`  | `label`  | Names the button. Defaults to Attach files.                                              |
| `ChatComposerMentionButton` | `label`  | Names the button. Defaults to Mention someone.                                           |
| `ChatComposerDropZone`      | `accept` | File types it takes. Match it to the attach button's.                                    |
| `ChatComposerDropZone`      | `label`  | Shown over the zone while files are dragged across it. Defaults to Drop files to attach. |

`ChatComposerInput` is named Message unless you pass `aria-label`, and
`ChatComposerSubmit` takes Button's props and is named Send when it has no
children.

</ExhibitCode>
</Exhibit>

### Edit message

Editing a sent message: a header says so, the footer swaps the actions for
Cancel and Save, and Escape cancels through the text box's own `onKeyDown`.
No `isEditing` prop.

<Exhibit
  of="chat-composer.EditMessage"
  description="Save, then press Edit to bring it back."
>
<ExhibitCode>

```tsx
<ChatComposerHeader>
  <PencilIcon />
  Editing message
</ChatComposerHeader>
<ChatComposerInput
  aria-label="Edit message"
  onKeyDown={(event) => event.key === "Escape" && cancel()}
/>
<ChatComposerFooter className="justify-end gap-2">
  <Button variant="ghost" onClick={cancel}>Cancel</Button>
  <ChatComposerSubmit>Save</ChatComposerSubmit>
</ChatComposerFooter>
```

### Synced draft

Two composers on one store, as a draft synced between a laptop and a phone
would be. Type in either one. The parts are the same; only the provider
changed.

<Exhibit of="chat-composer.SyncedDraft">

  const state = useSyncExternalStore(draft.subscribe, draft.get)

  return (
    <ChatComposerProvider state={state} actions={actions}>
      {children}

## Bring your own state

Every part talks to this interface and nothing else. Render
`ChatComposerProvider` with your own `state` and `actions` and the same parts
run on them:

```ts
type ChatComposerState = {
  value: string
  attachments: ChatComposerAttachment[]
  submitting?: boolean
  disabled?: boolean
  canSubmit?: boolean // defaults to having text or an attachment
}

type ChatComposerActions = {
  setValue: (value: string) => void
  addAttachments: (files: File[]) => void
  removeAttachment: (id: string) => void
  submit: () => void
}

type ChatComposerAttachment = {
  id: string
  name: string
  size?: number // bytes
  file?: File
}
```

Custom parts read the same context with `useChatComposer()`, which returns
`{ state, actions, meta }`, with the text box at `meta.inputRef`.

## Anatomy

Seven parts make up a full composer. Each is its own component, so a design
picks the ones it needs rather than switching features off. A provider holds
the draft and renders no element; a drop zone can wrap the frame, with no look
of its own until files are dragged over it.

## Guidelines

<UsageGuidelines
  guidelines={[
    "Compose a variant from parts instead of adding a prop. An edit box, a thread reply and a forward dialog are three compositions of the same parts.",
    <>
      Keep state out of the parts. If the draft has to survive a reload or
      follow someone across devices, swap <code>LocalChatComposerProvider</code>{" "}
      for a <code>ChatComposerProvider</code> fed by your store.
    </>,
    <>
      Put the provider around everything that needs the draft. A send button in
      a dialog's footer, outside the frame, still works when it's inside the
      provider.
    </>,
    <>
      Leave <code>ChatComposerCommonActions</code> out when a composer needs a
      different set, and list the actions it does need.
    </>,
    <>
      Return a promise from <code>onSubmit</code> when sending takes a round
      trip. The send button shows it's busy, and a rejection keeps the draft.
    </>,
  ]}
/>

## Accessibility

| Key                           | Does                                     |
| ----------------------------- | ---------------------------------------- |
| <Kbd>↵</Kbd>                  | Sends the draft                          |
| <Kbd>Shift</Kbd> <Kbd>↵</Kbd> | Breaks the line                          |
| <Kbd>Tab</Kbd>                | Moves to the actions and the send button |
