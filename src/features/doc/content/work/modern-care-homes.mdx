## What it is

Modern Care Homes is a senior living platform for the Phoenix metro. Families
search independent living and assisted living homes across Phoenix, Scottsdale,
Peoria, Paradise Valley, Queen Creek and Surprise, compare what they find, and
contact a home directly.

What makes it a hard design problem is that two pretty different people use it
for the same task. There's the resident, usually over 70, on a tablet or a
desktop with the browser zoomed way in, trying to figure out whether a place
looks like somewhere they could actually live. And there's their adult child, on
a phone, often in the middle of something stressful, trying to compare six homes
and find cost and care level fast.

They don't have much in common except that neither one has any patience for an
interface that gets in the way. Pretty much every decision I've made on this
project comes back to that.

## What I'm trying to do

<Steps>

<Step>Make homes easy to tell apart.</Step>

A directory is only useful if you can compare things. So the work is less about
how many results come back and more about whether you can look at two homes and
see the difference in care level, setting, and what's actually included.

<Step>Design from an accessibility floor instead of toward one.</Step>

The rule I hold everything to is that if it fails at 200% zoom, it isn't done.
Base type is 18px instead of 16. Minimum touch target is 48 by 48, which is
above the WCAG 2.2 floor of 44, because of who's using this. AA contrast is the
minimum and I'm going for AAA on body copy. None of that is a pass I do at the
end. It's where the layout starts.

<Step>Build a system instead of a pile of pages.</Step>

Every screen comes out of one component library and one set of tokens. Some of
that is speed, but mostly it's how the accessibility floor stays put. If it's
baked into the components, I can't accidentally undo it on page eleven.

<Step>Keep shipping.</Step>

This is ongoing, so there's no launch date to point at. The thing I actually
care about is whether it gets clearer every month.

</Steps>

## What I do

I'm the design engineer here, which in practice means I do the design and then I
build the front end of it.

- **Brand and visual direction.** Type scale, color, and the layout and
  photography language that makes a directory feel like a place instead of a
  spreadsheet.
- **Information architecture.** How homes get structured and compared, and what
  a family sees first when they land on one.
- **The design system.** Tokens, foundations, components. Foundations are
  locked. Components are still in progress and I'm publishing them as they get
  done.
- **Interface design.** Search, the listing and detail pages, contact, and the
  editorial pages that hold the posts and resources.
- **Front-end implementation.** I build what I design. Components, layout,
  responsive behavior, motion and accessibility all ship as code from me instead
  of as a spec I hand to someone else.
- **Accessibility.** Contrast, focus order, keyboard paths, zoom and target
  sizes get checked on the real build, because a mockup can't tell you what
  happens at 200 percent.

The part I like most is that I never have to defend any of it in a handoff
meeting. If something needs to change, I go change it.

## Working with Spencer

I build this with
[Spencer Grzincich](https://www.linkedin.com/in/grzincich/), a Software
Engineer.

He owns the data layer and the infrastructure. How home data gets modeled,
stored and served, the integrations, and everything that has to stay up. I own
everything a family sees.

The split works because there's almost nothing to translate between us. Normally
the expensive part of design and engineering working together is the handoff,
where a design gets described to someone who then rebuilds it from the
description. That step doesn't exist here, because I'm the one writing the
component. What Spencer and I actually negotiate is the shape of the data a
screen needs, and that's a short conversation we have once per surface instead
of a long one we have over and over.

## The stack

The front end is mine. Everything underneath it is Spencer's.

| Tool | Layer | Why |
| --- | --- | --- |
| Next.js (App Router) | Framework | Server rendering, because a lot of this traffic is a phone on cell service. Typed routes help as the directory grows. |
| React and TypeScript | UI | TypeScript catches the things I'd otherwise find in the browser. |
| Tailwind CSS | Styling | Tokens live as CSS variables, so a system change is one edit instead of forty. |
| shadcn/ui | Components | I own the source instead of importing it, so when I need to fix an accessibility issue I fix it inside the component. |
| Figma | Design | Where foundations and components live. Tokens map one to one with the CSS variables. |
| Vercel | Deployment | A preview build per branch, so I can look at a change on a real phone before it merges. |
| GitHub | Version control | Where the design and the code actually meet. |
| Spencer's side | Data and infrastructure | Home data, integrations, and everything that has to stay up. |

Nothing here is exotic. It's a pretty normal Next.js stack and that's on
purpose. The interesting part isn't the tools, it's that I'm not maintaining a
design and a separate implementation of it. When a token changes in Figma I
change it in `globals.css` and every screen follows.
